# Медиа Центр — единый рабочий процесс

Этот файл — главный источник правил разработки. `AGENTS.md` содержит короткие обязательные ограничения, `VIBE_CODING.md` — командную памятку, а `ROADMAP.md` — порядок следующих продуктовых и технических шагов.

## 1. Контекст проекта

Медиа Центр — внутренний SaaS для владельцев продуктов и редакторов контент-плана. В приложении есть рабочая панель, календарь, задачи, нагрузка, контент-план, справочники и настройки сайта. Основные требования продукта: быстрое заполнение, понятная связь план/факт, единый современный интерфейс и безопасное разделение гостевого просмотра и редакторских функций.

Техническая база:

- Next.js App Router, React, TypeScript и Tailwind/shadcn-подобный UI kit.
- Данные и авторизация могут использовать Supabase; переменные окружения читаются через `src/lib/supabase.ts`.
- В приложении есть существующий большой клиентский модуль `src/components/content-plan-fact-app.tsx`. Его постепенно разделяем по доменам, не переписывая продукт с нуля.
- Пакетный менеджер — npm. Источник зависимостей — `package-lock.json`.
- Production-репозиторий: `https://github.com/Tsay99/media-center.git`.
- Production-ветка: `main`.
- Vercel-проект: `content-plan-fact`, команда `tsays-projects`.
- Production-домен: `https://content-plan-fact.vercel.app`.

Бизнес-границы:

- Не менять API, схему базы, RLS или авторизацию в рамках обычной UI-задачи.
- Изменения данных, ролей и миграций оформлять отдельной задачей с описанием обратной совместимости.
- Гостю показываются только разрешённые страницы. Редакторские страницы и справочники не должны появляться в гостевом меню.
- Бизнес-логику публикаций, распределения часов, календаря, задач и undo сохранять при визуальном рефакторинге.

## 2. Источник истины и окружения

GitHub — единственный источник истории и кода. Vercel подключён через Git Integration:

~~~text
feature branch → Pull Request → Vercel Preview → review/CI → merge в main → Production
~~~

Правила:

- `main` соответствует production и не используется для прямой разработки.
- `codex/*` — короткоживущие ветки отдельных задач.
- Production не публикуется из незакоммиченного рабочего дерева.
- `vercel --prod` разрешён только для аварийного восстановления или rollback, когда Git Integration недоступен.
- `.env.local`, токены, пароли, service-role ключи и персональные credentials не коммитятся.
- Preview не считается релизом, пока не проверены пользовательский сценарий, CI и риски.

## 3. Жизненный цикл задачи

### 3.1. Вход задачи

Перед кодом фиксируются:

1. пользовательский результат одним предложением;
2. затронутые страницы и сущности;
3. критерии готовности;
4. ограничения: данные, роли, responsive, accessibility, обратная совместимость;
5. способ проверки и необходимость миграции.

Задача готова к работе, если понятно, что должно измениться и как доказать результат. Не начинать реализацию по одному скриншоту без проверки существующего поведения.

### 3.2. Изоляция

Из `main` после синхронизации создаются отдельные ветка и worktree:

~~~powershell
cd D:\media-center
git fetch origin
git switch main
git merge --ff-only origin/main
git worktree add ..\media-center-<task> -b codex/<task> origin/main
cd ..\media-center-<task>
~~~

Примеры имён:

~~~text
codex/calendar-filters
codex/site-settings
codex/tasks-completion
codex/ui-header
~~~

Не редактировать `main` напрямую для feature-задачи. Один агент отвечает за одну задачу, одну ветку, один worktree и один PR. После merge удалить worktree только если в нём нет незакоммиченных изменений.

### 3.3. Реализация

- Сначала искать существующий компонент, токен или хелпер; не создавать второй вариант того же UI.
- Общие правила цветов, типографики, spacing, radius, теней, focus и motion держать в общей дизайн-системе.
- Одинаковые select, tooltip, dropdown, dialog, карточки, page header, loading, empty и error states должны иметь одинаковое поведение.
- Анимации быстрые и функциональные: CSS transitions или уже установленная библиотека; новую тяжёлую зависимость добавлять только с обоснованием.
- Клик по управляющему элементу не должен случайно открывать родительскую карточку; использовать `stopPropagation`, когда это требуется.
- Для интерактивов обязательны клавиатура, `aria-label`, видимый focus и понятное disabled-состояние.
- Не ломать мобильную сетку: сначала проверить узкую ширину, затем desktop.
- Большой `content-plan-fact-app.tsx` не изменять параллельно несколькими агентами. При доменном изменении по возможности сначала вынести независимый модуль.

### 3.4. Локальная проверка

Из корня feature-worktree:

~~~powershell
npm ci
npm run typecheck
npm run lint
npm run build
git diff --check
~~~

Если в проект добавлен тестовый скрипт, запускать также:

~~~powershell
npm test
~~~

Сейчас отдельного `test` script нет; это зафиксировано в `ROADMAP.md`. Ошибки окружения отделять от ошибок кода и записывать в PR. Не считать задачу готовой только потому, что dev-server стартовал.

### 3.5. Commit и PR

Коммиты маленькие и смысловые, Conventional Commits:

~~~text
feat(calendar): add multi-product filters
fix(sidebar): restore collapsed navigation
refactor(ui): extract shared page header
test(distribution): cover reels limits
docs(workflow): define development rules
~~~

Перед push:

~~~powershell
git status --short
git diff --check
git add <нужные-файлы>
git commit -m "<conventional commit>"
git push -u origin codex/<task>
~~~

В PR обязательно указать:

- что увидит пользователь;
- какие файлы и слои затронуты;
- команды проверок и их результат;
- Preview URL Vercel, если он создан;
- риски, миграции и что сознательно не менялось.

### 3.6. Review, merge и release

1. Проверить diff и отсутствие случайных файлов/секретов.
2. Проверить CI на pull request.
3. Открыть Preview Vercel и проверить основной сценарий, responsive и доступность.
4. Выполнить review; review-агент анализирует diff и не меняет файлы.
5. Merge PR в `main` через GitHub.
6. Дождаться production deployment Vercel и проверить URL/статус.
7. Зафиксировать результат в PR или release note.
8. Удалить feature-ветку и worktree после подтверждения, что они больше не нужны.

Rollback — это отдельное осознанное действие: сначала остановить продвижение, затем вернуть предыдущий проверенный deployment Vercel или сделать revert-коммит. Не использовать destructive Git-команды для исправления обычной ошибки.

## 4. Роли и параллельная работа

Для небольшой задачи достаточно одного агента. Для крупной задачи координатор делит работу по границам:

- Coordinator — уточняет критерии, выбирает архитектуру, собирает итог, делает финальный review.
- UI — компоненты, дизайн-токены, responsive, motion и accessibility.
- Logic — состояние, расчёты, фильтры, переходы план/факт, сохранение данных.
- QA — сценарии, typecheck/lint/build, регрессии и ручная проверка Preview.
- Review — только анализ diff, риски и рекомендации; файлы не изменяет.

Параллелить можно только независимые области. Нельзя одновременно править один и тот же большой файл или одну и ту же бизнес-функцию. Сначала согласовать контракт данных, потом объединять изменения.

## 5. Definition of Ready / Done

### Ready

- Понятен пользовательский результат.
- Названы роли и страницы.
- Есть критерии успеха и способ проверки.
- Понятно, затрагиваются ли API, БД, auth или миграции.
- Выбраны ветка/worktree и ответственный агент.

### Done

- Реализованы критерии задачи без лишней бизнес-логики.
- Обновлены общие компоненты/токены, если изменение повторяемое.
- Есть loading, empty, error, disabled, focus и mobile-состояния там, где они применимы.
- Пройдены typecheck, lint, build, diff check и тесты, если они есть.
- PR содержит результат, риски и Preview.
- PR прошёл review и CI; после merge production подтверждён.
- Документация/дорожная карта обновлены, если изменился процесс или архитектура.
